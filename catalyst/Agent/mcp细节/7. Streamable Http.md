# treamable HTTP transport
**MCP（Model Context Protocol）里的 Streamable HTTP transport**，不是 HTTP/1.1、HTTP/2、HTTP/3 那种“新版本 HTTP”。它是 MCP 在 2025-03-26 规范里引入、用来替代旧 **HTTP+SSE** 的远程传输方式。现在做远程 MCP Server，基本都优先选它。

## 一句话理解

**Streamable HTTP = 用一个 HTTP 端点承载 MCP 的 JSON-RPC 消息；客户端用 POST 发消息，服务器可以用普通 JSON 回，也可以用 SSE 流式回。**

典型端点是：

```text
https://example.com/mcp
```

## 为什么流行？

旧的 MCP HTTP+SSE 模式大概是：

1. 客户端先 `GET /sse` 建一条 SSE 长连接；
2. 服务器通过 SSE 发一个 `endpoint` 事件，告诉客户端往哪个 `/messages` 发消息；
3. 客户端再 `POST /messages` 发 JSON-RPC。

问题很多：

- 必须维持长连接；
- 双端点，网关、代理、Serverless 都不友好；
- 负载均衡要粘性会话；
- 很难做无状态部署；
- 断线恢复麻烦。

Streamable HTTP 把它们统一成：

- 一个端点，例如 `/mcp`；
- 客户端 `POST /mcp` 发 JSON-RPC；
- 服务器可以返回 `application/json`，也可以返回 `text/event-stream`；
- 服务器主动推送可以通过可选 `GET /mcp` 的 SSE 流；
- 支持 `Mcp-Session-Id` 会话；
- 支持 `Last-Event-ID` 断线恢复；
- 可以无状态，也可以有状态。

所以它特别适合云函数、Serverless、边缘计算、Kubernetes 多副本、API Gateway 这类环境。

## 核心工作方式

客户端请求一般长这样：

```http
POST /mcp HTTP/1.1
Content-Type: application/json
Accept: application/json, text/event-stream
MCP-Protocol-Version: 2025-06-18
Mcp-Session-Id: abc123

{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"add","arguments":{"a":1,"b":2}}}
```

服务器有两种主要返回：

### 1. 普通 JSON 响应

适合快速工具调用：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"3"}]}}
```

### 2. SSE 流式响应

适合进度、日志、通知、长任务：

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache

id: 42
event: message
data: {"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"3"}]}}
```

SSE 里的 `data` 仍然是 JSON-RPC 消息。服务器可以在同一个流里先发通知、进度，再发最终响应。

如果客户端 POST 的只是通知或响应，服务器通常返回：

```http
202 Accepted
```

## 有状态 vs 无状态

### 无状态模式

每个请求独立，不依赖 session。适合：

- Cloudflare Workers；
- Vercel / Netlify Functions；
- AWS Lambda；
- 水平扩展的多副本服务。

FastMCP 里可以这样开：

```python
from mcp.server.fastmcp import FastMCP

mcp = FastMCP("demo", stateless_http=True)

@mcp.tool()
def add(a: int, b: int) -> int:
    return a + b

mcp.run(transport="streamable-http")
```

默认端点通常是：

```text
http://127.0.0.1:8000/mcp
```

### 有状态模式

初始化时服务器可以返回 `Mcp-Session-Id`：

```http
Mcp-Session-Id: abc123
```

后续客户端请求都带上它。服务器可以：

- 维护会话状态；
- 主动向客户端发请求，比如 sampling、roots、elicitation；
- 支持断线恢复；
- 支持多个 SSE 流。

客户端结束会话时可以：

```http
DELETE /mcp
Mcp-Session-Id: abc123
```

## 和旧 HTTP+SSE 的区别

| 对比项 | 旧 HTTP+SSE | Streamable HTTP |
|---|---|---|
| 端点 | `/sse` + `/messages` | 通常单端点 `/mcp` |
| 客户端发消息 | POST `/messages` | POST `/mcp` |
| 服务器回消息 | SSE 长连接 | POST 响应 JSON 或 SSE |
| 服务器主动推送 | 依赖 SSE 长连接 | 可选 GET `/mcp` SSE |
| 无状态部署 | 很难 | 支持 |
| Serverless | 不友好 | 友好 |
| 断线恢复 | 麻烦 | 支持 `Last-Event-ID` |
| MCP 官方态度 | 旧方案，兼容用 | 当前推荐远程传输 |

## 实现时容易踩的坑

1. **Accept 头必须同时包含**  
   `application/json` 和 `text/event-stream`。

2. **代理可能缓冲 SSE**  
   Nginx、CDN 要关闭缓冲，比如 `X-Accel-Buffering: no`。

3. **CORS 要放行相关头**  
   常见有 `Mcp-Session-Id`、`MCP-Protocol-Version`、`Last-Event-ID`。

4. **安全**  
   校验 `Origin`，本地服务绑定 `127.0.0.1`，公网走 HTTPS，认证通常用 OAuth 2.1。不要裸奔。

5. **会话 ID 不可预测**  
   要随机、可过期、绑定用户或租户，不能当普通自增 ID 用。

6. **无状态模式不能依赖服务器主动推送**  
   如果你需要 sampling、elicitation、断线恢复，通常要有状态和 SSE 流。

## 总结

Streamable HTTP 不是新 HTTP 协议，而是 **MCP 的现代远程传输方案**：

- 单端点；
- POST 发 JSON-RPC；
- 可返回 JSON，也可返回 SSE；
- 支持无状态和有状态；
- 支持会话、恢复、服务器主动消息；
- 对 Serverless、网关、多副本部署更友好。

现在远程 MCP Server 基本默认选它；本地工具仍然常用 stdio；旧 HTTP+SSE 主要留给兼容老客户端。
